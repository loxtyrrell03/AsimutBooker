# Asimut Booker UX audit — 8 September 2026

The audit followed desktop navigation, Calendar edits, preference persistence,
phone navigation, live schedule refresh, Assistant delivery and recovery, and
the booking-selection behavior behind the reported early-morning reservation.
Tests used temporary settings and intercepted APIs; they did not create or
cancel reservations or edit the user's saved preferences.

| Failure | User impact | Repair and evidence |
| --- | --- | --- |
| Desktop status refresh rebuilt Calendar date variables | Unsaved current and future date selections disappeared | Merge untouched saved dates while retaining edited controls and their baseline; isolated Tk regression reproduced the failure before repair |
| Delayed process-launch error callback referenced a cleared exception | The useful failure message was replaced by a callback error | Capture the message when the exception occurs; regression reproduces a failed launch |
| Leaving phone Settings unmounted the editor | A draft disappeared when visiting Today or Assistant | Preserve the mounted editor across tabs; mobile Chromium and WebKit navigate away and back with edits intact |
| Switching practice dates replaced the previous date's draft | Save applied only the last date selected | Stage edits per date and save all changes atomically; multi-date regression verifies saved hours and disabled dates |
| Settings loads and saves could remain pending indefinitely | Loading/Saving and disabled controls stranded the user | Bound complete JSON responses, allow load cancellation, ignore cancelled results, and require a fresh read after uncertain writes |
| A delayed message acknowledgement cleared a newer draft | Text typed while waiting was lost | Clear only the acknowledged text; check preservation with delayed responses |
| An uncertain delivery could only be retried by replacing the current draft | The next draft obstructed safe recovery | Add an explicit retry of the original message ID and text; preserve the newer draft and never retry automatically |
| Stop ignored HTTP rejection | Stop appeared to do nothing | Check the response and show that stopping was not confirmed; rejected-Stop regression |
| New-chat replies and older snapshots arrived after newer stream updates | The Assistant could appear busy again or lose current state | Stream events own reset state; reject older same-generation snapshots and refresh after reset acknowledgement |
| Action errors also rendered a connection banner | The app said Connecting despite a working connection | Show action errors once, independently of connection status |
| Refresh silently returned during an Assistant turn | Tapping the button appeared ineffective | Explain that the user must wait for the active Assistant task |

## Morning reservation

The local run log at `logs/2026-09-08/13-13-02.log` records preferences of
12:00–18:00 with strict mode off. After saving 12:45–13:15, the planner selected
08:00–08:30 in Weston Gallery for 15 September to increase coverage of the
three-hour daily target. Preference distance was not an acceptance criterion.

The separate task, **Penalize bookings far from preferred**, owns the booking
policy repair. Its shared-checkout implementation uses repeatable exponential
time weights and a minimum useful score, allowing nearby alternatives while
leaving capacity unfilled for very undesirable starts. The audit's full Python
run passed 772 tests with that implementation present, including a regression
for the reported day's selection. The audit did not cancel the existing booking.
